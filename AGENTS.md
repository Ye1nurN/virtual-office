# Правила работы с репозиторием

## Автоматическое сохранение завершённой работы в GitHub

Постоянное указание пользователя от 2026-09-29: после завершения работающего изменения самостоятельно создавать коммит и отправлять его в GitHub. Отдельное напоминание или подтверждение на обычные `git commit` и `git push` не требуется. Более поздняя просьба пользователя не коммитить или не отправлять изменения отменяет это действие для соответствующей задачи.

1. В начале работы проверь `git status`, текущую ветку, upstream и существующие изменения. Сохраняй чужие и незавершённые изменения; не включай их в свой коммит.
2. Выполни согласованную задачу до рабочего результата. Обсуждение идей, исследование и промежуточное редактирование сами по себе не требуют коммита. Отправляй завершённые логические изменения, а не каждое сохранение файла.
3. Перед коммитом проверь diff и выполни подходящие проверки. Для изменений кода `city-demo`: `npm test` и `npm run build` из этой папки; для UI, 3D и взаимодействий также проверь затронутый сценарий в браузере. Для `office-demo` следуй его локальным правилам. Для изменений только документации достаточно проверки содержимого и `git diff --check`.
4. Проверки должны относиться к коду, который попадёт в коммит. Не полагайся на незакоммиченные зависимости из другой задачи. Если изменения пересекаются, сначала отдели свою работу без потери существующих правок; если безопасно отделить её нельзя, сообщи конкретную причину.
5. Добавляй в индекс только относящиеся к задаче файлы или фрагменты. Проверь staged diff, состав исходящих коммитов и отсутствие секретов, `.env`, зависимостей, локальных логов и сборочных артефактов. Не используй безусловный `git add .` или `git add -A` для всего репозитория.
6. Если проверки прошли, создай коммит с понятным описанием результата и выполни обычный push в upstream текущей рабочей ветки. Если upstream отсутствует, используй одноимённую ветку в проверенном `origin`; новые рабочие ветки называй с префиксом `codex/`. Для существующей работы в `master` допустим `origin/master`. Не переключай ветку и не сливай её в `master` только ради автосохранения.
7. Не применяй force push, не обходи защиту веток и не переписывай чужую историю. При отказе push проверь причину и безопасно устрани её; если необходим вход, доступ или решение пользователя, сохрани локальную работу и сообщи, что именно не удалось отправить.
8. Проверь, что коммит появился в удалённой ветке. В финальном ответе укажи результат, выполненные проверки, короткий SHA, ветку и статус push. При неуспешных проверках исправь проблему; не отправляй код с известной поломкой и не называй его проверенным.

## GitHub и публикация сайта

- Основной remote: `https://github.com/Ye1nurN/virtual-office.git`. Перед отправкой проверяй фактический remote.
- Push в ветку, подключённую к Cloudflare Pages, может запустить автоматическую публикацию. Это ожидаемая часть указанного пользователем процесса.
- Успешный push не означает успешный деплой. Если задача включает обновление сайта, проверь статус сборки и опубликованный результат. Не утверждай, что сайт обновился, только по факту коммита.
- Приложение города находится в `city-demo`; параметры Pages — в `city-demo/CLOUDFLARE.md`. Сохраняй исходный `office-demo` при работе над городом.
- Изменение правил доступа, удаление данных и настройка аккаунтов не входят в разрешение на обычный commit/push.
